## 2. Where the implementation departs from the prototype, and why

| Prototype | Implementation | Reason |
|---|---|---|
| Runtime **topology** (browser → frontend → backend → database, probes per service) | Runtime **proof chain**: Test Room gates → recorded probes, then live preview → browser console; a dashed card names G6 | The backend serves gates with evidence and one preview session. It serves no list of services with ports, no latency history and no restart count; drawing a topology would invent it. |
| Mission map stations Idea, Discovery, Requirements, Architecture → Company, Jobs, Build, Test, Runtime, Delivery | Definition (room status), Requirements (PromptMaster version), Architecture (blueprint version), Review (generation readiness) → Company (`virtualCompany.status`), Generation (job status; stages hang below from `stageStatuses`), Build (`buildStatus`), Quality gate (kernel blockers), Certification (kernel phase), Delivery gate | These are the stations the reads answer. Quality, certification and delivery are read for **the project this mission generated** (`job.generatedProjectId`), not for the room's latest mission. |
| Ten-point mission line in every list | Five points (definition, requirements, generation, build, package) and a dashed tail | A list cannot read the kernel or the delivery decision without one request per project (gap G5). The project screens draw the rest. |
| Action Center merges `/inbox` and `/platform/decisions` | Kept apart | `/platform/decisions` lists model-routing decision traces (observability), not decisions a person takes. One queue would give "decision" two meanings. |
| Seat ring with five fixed axes | One arc per axis the role's latest cognitive run recorded | The number of axes per run varies in the backend; a missing run is a dashed ring, never an empty pass. |
| Architecture map of routes → API modules → tables | Requirements cited → decisions by layer (experience, contract and access, core, data and operations) with dependency arrows | The served blueprint is a list of decisions per area, each with the requirement excerpts it cites and its dependencies as text. A dependency is drawn only when its words name a decided area; the rest stay in the inspector as written. |
| Six screen transitions: Command Center → Mission, Mission → Agent, Mission → Runtime, Runtime → Evidence, Evidence → Test, Action Center → Decision | The chosen element travels into the destination's title: a project on the Command Center board → its cockpit; a decision (queue item, Inbox card) → the screen that takes it; a seat on the company map → its agent; a station on the mission map → its screen; a unit of work → its job; a mission's latest Test Room gate line → Runtime; the runtime chain's heading → Evidence; the Test room panel of Evidence → Runtime and → Test Room; a Test Room gate on the evidence graph or the runtime chain → its session in the Test Room; a session on Verification → the Test Room | There is no decision page: a decision opens the screen where it is taken. The morph waits at most 300 ms for a title that is not `aria-busy` (the cockpit shows the room key while the name loads) and otherwise fades, so it never waits on data and never lands on a key. |
| Runtime and Evidence belong to "the project" | Runtime and Evidence read the project the latest generating mission produced, unless a mission is named (`?mission=`). A mission's "Runtime and evidence" panel, its evidence stations on the mission map, and the links between Runtime and Evidence carry the mission; each screen names the mission it reads for and links back to it | Every generation writes its own project id (`ProjectWriter.write`), so an earlier mission's runtime and evidence are not the latest one's. A screen that reads an earlier mission's project says so and offers the latest; a mission the project does not list is named as such, never swapped for the latest; a named mission without a generated project says it has none. Chief verification is read for the named mission. |
| Test Room (`#/app/tests`): run stages at real timestamps, one square per test, a browser E2E storyboard, "Run again" | Test Room (`/p/{key}/evidence/test-room`, `?session=`, `?mission=`): the steps of a stored session placed at their `observed_at` between `started_at` and `finished_at`; each gate with its blockers, warnings and every piece of evidence (command, exit code, HTTP status, duration, process handle and port, artifact path and SHA-256, the reason a step did not run); the session record and the history, with the passing session on record marked; "Run again" shows the run's verdict and the application output it returned | A stored session records the test runner's command, exit code and duration — no result per test — and Test Room sessions carry no browser checks (those belong to stack certification). Squares and a storyboard would be drawn from nothing, so the page says what is recorded instead. The application output (`logs_tail`) is returned by `POST …/run` but not served for stored sessions, so it appears only after a run started from the page. Durations are shown as numbers, never as bars stretched back from the moment a step was observed. |
| Engineering Workbench trace requirement → jobs → agents → files → build → tests → evidence | requirement → unit of work → agent → stage → files → build → Test Room gates | Executions name their `blueprint_ref`, agent and `stage`; artifacts name the `stage` they were written in. No read says which agent wrote which file, so files hang from the stage, and the inspector says the author is not recorded. |
| Technology graph languages → frameworks → compositions ← infrastructure | language → build profile (verdict of its latest component certification, `EXPERIMENTAL` when none, `unknown` when the ledger could not be read) → composition | Infrastructure is not served as a set of nodes. A composition's ledger rows record one `stack_id`; its other members are not served, so the inspector names them as missing instead of parsing them out of the composition id. |
| Login art with the thesis line and coordinates | The same story drawing in the sign-in column, above the product points; hidden below 1024 px | In one column the form is the job. The map is visible from the first frame and only the path animates, so a still frame (thumbnail, slow device) never shows an empty rail. |
| Evidence pillars Build, Tests, Runtime, Quality gate, Gatekeeper | Build, Tests, Quality gate, Chief verification, Functional completeness, plus Release (`can_release`) | Those are the verdicts served (kernel, Test Room proof, quality report, Chief). Kernel evidence items are grouped under a pillar by the words in their id; an item that matches none attaches to the verdict. Chief dimensions use the backend's own words (ok, incomplete, blocked, unavailable). |

## 3. Truth rules, as enforced in code

- A read that failed or has not answered is `unknown` and drawn dashed; a step that cannot exist yet is `NOT_RUN`. Neither is ever drawn as proof.
- Motion only answers a state: the breathing ring and the spinning arc exist only while the backend reports a running state; the signal strip glows once for a new event; the settle ring fires only when a family changed between two reads; the camera moves only when a person moves it or the drawing changes shape. Reduced motion (OS or in-app) turns all of it into cuts.
- Endpoints (`<Source>`) and raw ids (`.dev-only`) stay in the DOM and show only with **Developer details** on.
- Every drawing has a text path: canvas nodes are focusable buttons named "Label: STATE", and the tables (activity, seats, certification, coverage) remain as the text view. Illustrations are `aria-hidden` beside words that already say the state; the sign-in story is one `img` named by its stations.
- A join is drawn only through a served field: job dependencies (`dependency_job_ids`), requirement references (`requirement_refs`), `blueprint_ref`, `stage`, `profile_id`, `stack_id`. Nothing is parsed out of an id or a title.
- Backend words are shown verbatim; technology names are never translated; the four locales stay at parity (the typecheck enforces it).
