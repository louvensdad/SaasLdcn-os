# LGPD Handling Standard

## Rule

Personal data collected by LDCN OS (account/profile data) must always be
processed under explicit, recorded consent, must be exportable to the data
subject on request, and must be erasable (via anonymization) on request.
Authentication and authorization controls must protect this data from
unauthorized access.

## Personal data inventory

The only personal data stored by the backend is the `users` table
(`apps/api/app/repositories/user_repository.py`):

- `email`, `full_name` -- identifying data, provided at registration.
- `hashed_password` -- never stored or returned in plaintext (bcrypt via
  `app/core/security.py`).
- `locale` -- user preference, not sensitive.
- `consent_accepted_at`, `consent_policy_version` -- consent record (Art. 8).
- `created_at`, `updated_at` -- account lifecycle timestamps.

Projects, blueprints, templates, and other workspace data generated by LDCN
OS are build artifacts, not personal data tied to an individual account in
this version, and are therefore out of scope for export/erasure requests.

## Required behavior

- **Consent (Art. 8)**: `POST /api/auth/me/consent` records
  `consent_accepted_at` (UTC timestamp) and `consent_policy_version`
  (`Settings.privacy_policy_version`). Consent with `accepted: false` is
  rejected (`400`) -- the platform cannot operate without it, so users who
  do not consent should not create an account rather than hold a
  non-consenting account.
- **Access / portability (Art. 9, 15, 18)**: `GET /api/auth/me/export`
  returns all personal data held about the requesting user as a single JSON
  document (`DataExportResponse`). Only the authenticated user can export
  their own data -- there is no admin "export any user" endpoint.
- **Erasure (Art. 18)**: `DELETE /api/auth/me` anonymizes the account
  (`UserRepository.anonymize_user`): email is replaced with a non-reversible
  placeholder, the password hash is cleared (the account can never
  authenticate again), `full_name` is replaced, `is_active` is set to false,
  consent fields are cleared, and all outstanding refresh tokens are revoked.
  The row is kept (not hard-deleted) so the audit trail keeps a stable,
  non-identifying `user_id`; this is anonymization, not deletion of the
  account record itself.
- **Audit trail (Art. 37)**: every sensitive account event is recorded in the
  `audit_logs` table via `AuditLogRepository` -- registration, login,
  failed login, logout, password change, consent, data export, account
  deletion, and token refresh (`AuditLogRepository.SAFE_EVENT_CODES`).
  Audit entries store only `user_id`, an event code, and a timestamp -- never
  passwords, tokens, or other personal data values. Events tied to the
  requesting account are included in the personal-data export.
- **Security of processing (Art. 46)**:
  - Passwords are hashed with bcrypt (`app/core/security.py`), never logged
    or returned.
  - Access to all personal-data endpoints requires a valid JWT access token
    (`app/core/deps.get_current_user`), enforced globally in
    `app/main.py` via `app.include_router(..., dependencies=[Depends(get_current_user)])`.
    Only `/api/health`, `/api/auth/*`, and `/api/localization/*` are public.
  - Refresh tokens are tracked per-`jti` and can be individually revoked
    (logout) or bulk-revoked (password change, account deletion). Browsers
    receive them only as `HttpOnly`, `SameSite=Lax` cookies; response bodies
    and browser storage contain only the short-lived access token.
  - Security response headers (`app/core/security_headers.py`) and rate
    limiting on auth endpoints (`app/core/rate_limit.py`, production only)
    reduce the attack surface for credential theft and brute-forcing.
  - CORS is restricted to an explicit origin allowlist
    (`LDCN_ALLOWED_ORIGINS`), explicit methods, and explicit headers
    (`app/core/cors.py`) -- never `allow_origins=["*"]` with credentials.
    Production starts with no allowed origins unless the allowlist is set.
  - Production refuses to start without `LDCN_SECRET_KEY`; ephemeral JWT
    signing keys are allowed only for local development.

## Retention and minimization

- Expired refresh-token records are deleted during repository startup.
- Audit events are retained for `Settings.audit_log_retention_days` (730 days
  by default); older entries are deleted during repository startup.
- Anonymized account rows contain no active credentials, consent record,
  name, or reachable email address. They remain only as non-identifying
  referential anchors for the retained audit trail.
- Raw passwords, access tokens, refresh tokens, provider secrets, request
  bodies, and personal-data values are never written to audit logs.

## Data subject request mapping

| LGPD right | Endpoint |
| --- | --- |
| Confirm processing / access (Art. 9, 18 I-II) | `GET /api/auth/me` |
| Correction (Art. 18 III) | `PATCH /api/auth/me` |
| Portability (Art. 18 V) | `GET /api/auth/me/export` |
| Anonymization / erasure (Art. 18 IV, VI) | `DELETE /api/auth/me` |
| Revoke consent (Art. 8 §5, Art. 18 IX) | `DELETE /api/auth/me` (erasure also clears consent) |

## Out of scope / known limitations (this pass)

- Projects/generated artifacts are not yet scoped per-user (no `user_id`
  ownership column), so they are intentionally excluded from export/erasure.
  If per-user project ownership is added later, this document and
  `AuthService.export_data` must be updated together.
- Audit events are exported to the account holder and expire according to the
  retention policy above. They are not individually editable because they are
  an integrity record.
